# Design

## Context

See `proposal.md` — Why. What shapes the approach, observed in `lib/`:

- `DataLayer.bulk_create/3` (`lib/ash_clickhouse/data_layer.ex:454`) enumerates the changesets into `Insert.changeset_to_insert_attrs/2` results, runs them through `Insert.attrs_to_row/2` and `Insert.build_insert_rows/2` to produce the **encoded** rows, chunks those rows, and — when `return_records?` is true — returns `stream_bulk_records(rows, resource)` (`data_layer.ex:822`), which is `Stream.map(rows, &Record.to_ash_record(&1, resource))`. The rows it maps over are the wire rows.
- `DataLayer.do_insert/4` (`data_layer.ex:745`), the single-record path, does the same insert but returns `Record.to_ash_record(attrs, resource)` — the **submitted** attributes (`data_layer.ex:752`). The two paths therefore differ in what they hand back.
- `Insert.build_insert_rows/2` (`lib/ash_clickhouse/data_layer/insert.ex:22`) is the only place the wire encoding happens; `encode_bulk_value/3` (`insert.ex:235`) maps a `%DateTime{}` to a quoted decimal Unix-seconds string, a `%Date{}` to days since the epoch, and so on.
- `Record.to_ash_record/2` (`lib/ash_clickhouse/data_layer/record.ex:50`) turns a row (list) or an attribute map into a resource struct, running each attribute through `Types.decode_value/2` (`lib/ash_clickhouse/data_layer/types.ex:277`).

The Ash-side contract that the bulk return path currently violates:

- `Ash.Actions.Create.Bulk` matches a record returned by the data layer back to the changeset that produced it. `index_changesets/1` (`deps/ash/lib/ash/actions/create/bulk.ex:1041`) builds `changesets_by_ref` keyed by `changeset.context.bulk_create.ref` and `changesets_by_index` keyed by `changeset.context.bulk_create.index`; the returned record is looked up through `Ash.Actions.Helpers.Bulk.lookup_changeset/4` (`bulk.ex:1515`), which reads `record.__metadata__[:bulk_action_ref]` or `record.__metadata__[:bulk_create_index]`.
- With neither key present the lookup yields `nil`, and that `nil` changeset reaches `Ash.Actions.ManagedRelationships.load/4` (`deps/ash/lib/ash/actions/managed_relationships.ex:21`). Its guards only match a map that *has* a `:relationships` key, so `nil` falls through to `Enum.reduce_while(changeset.relationships, ...)` and raises `BadMapError: expected a map, got: nil`.
- `AshPostgres` — the reference data layer — satisfies this by tagging each returned record itself: `Ash.Resource.put_metadata(result, :bulk_action_ref, changeset.context[:bulk_create][:ref])` (`deps/ash_postgres/lib/data_layer.ex:2925`).
- `Ash.Actions.Helpers.Bulk.put_metadata/2` (`deps/ash/lib/ash/actions/helpers/bulk.ex:236`) is the public helper for this: it sets `:bulk_create_index` and `:bulk_action_ref` from the changeset's bulk context, and its final clause returns the record unchanged when the changeset carries no bulk context.
- Ash sorts the returned records by `__metadata__.bulk_create_index` (`bulk.ex:1115`), so that key also determines the order the caller sees.
- `Ash.load(records, select, reuse_values?: true, ...)` (`bulk.ex:1759`) does not re-read the values already present on the record, so whatever type the data layer put there is the type the caller receives.

## Goals / Non-Goals

**Goals:**

- `Ash.bulk_create/4` with `return_records?: true` completes and returns one correctly-typed record per inserted row.
- The wire encoding stops being observable in the returned record.
- The two write paths (`create` and `bulk_create`) return the same kinds of values for the same inputs.

**Non-Goals:**

- Changing what is written to ClickHouse. The encoded rows, the chunking, the batch size and the insert options are untouched.
- Changing `Types.decode_value/2`. The read path still returns a `:date` attribute as the raw string ClickHouse sends (`"2024-01-02"`); that is a separate defect with a separate fix.
- Changing the single-record `create` path — it already returns the submitted values.
- Reading rows back from ClickHouse after the insert.
- Any public API, DSL, schema or dependency change.

## Decisions

### 1. Build the returned records from the submitted changeset attributes, not from the encoded rows

`bulk_create/3` already computes `Insert.changeset_to_insert_attrs/2` for every changeset. Those attribute maps are the values the caller submitted (plus the autogenerated primary keys the insert needs) — the same input `do_insert/4` hands to `Record.to_ash_record/2`. The change keeps those maps and derives the returned records from them, in that order:

```
   changesets
       |
       +--> changeset_to_insert_attrs  --> attrs (submitted values)
       |                                        |
       |                                        +--> Record.to_ash_record(attrs, resource)
       |                                             +--> put_metadata(record, changeset)
       |                                             =--> returned records
       |
       +--> attrs_to_row --> build_insert_rows --> encoded rows
                                                    |
                                                    +--> repo.insert_rows(...)  =--> ClickHouse
```

The encoded rows become a wire-format concern only. They are no longer reused to reconstruct the record.

**Alternatives considered:**

- *Decode the encoded rows back into Ash values* (make `Types.decode_value/2` the inverse of the encoder). Rejected. The `DateTime64` encoder always emits six fractional digits regardless of the column's precision, and ClickHouse's `DateTime64` text parser discards digits beyond the column's scale (`src/IO/ReadHelpers.h`, `readDateTimeTextImpl`: *"Ignore digits that are out of precision"*). The wire form therefore never carries the column's truncation, so decoding it back reproduces the **submitted** value, not the **stored** one — the same answer this decision gives, for more machinery. It would also force `Types.decode_value/2` to accept two different wire formats (the encoder's decimal string and ClickHouse's `"YYYY-MM-DD hh:mm:ss.ffffff"`), and it would collapse the `NaiveDateTime` distinction, because the encoder normalises naive datetimes through `Etc/UTC` and reversing that is guesswork.
- *Read the rows back from ClickHouse after the insert.* Rejected. It costs an extra round trip per chunk, and ClickHouse has no `RETURNING`; `doc/querying.md` already states that returned records are locally reconstructed rather than re-read.
- *Keep the encoded rows and add a separate inverse encoder beside `Types.decode_value/2`.* Rejected for the same reason as the first alternative, and it leaves two encoders to keep in step.

### 2. Attach the bulk correlation metadata with `Ash.Actions.Helpers.Bulk.put_metadata/2`

Each returned record is tagged with Ash's bulk helper, which sets `:bulk_create_index` and `:bulk_action_ref` from the changeset's bulk context.

Why this helper rather than `Ash.Resource.put_metadata(result, :bulk_action_ref, changeset.context[:bulk_create][:ref])` (what `AshPostgres` does): it also sets the index that Ash uses to order the records, and its final clause returns the record unchanged when the changeset has no bulk context. That matters because the data layer is also called directly — the unit tests call `DataLayer.bulk_create/3` outside any bulk action, and a changeset built that way has no `bulk_create` context, so reaching into `changeset.context.bulk_create.ref` unguarded would raise.

Why it matters at all: without the reference, Ash cannot map a returned record back to its changeset, and the write path fails after the rows are already committed to ClickHouse.

### 3. Keep the chunking, the error handling and the `return_records?` semantics as they are

The chunk loop, `handle_result/1`, the `batch_size` cap and the "no cross-chunk rollback" behaviour are unrelated to this defect and stay exactly as they are. Only the source of the returned record changes.

### 4. Do not touch `Types.decode_value/2`

The read path's `:date` gap — no `:date` entry in the `@type_dispatch` table (`types.ex:253`), so a `:date` attribute read back from ClickHouse stays the string `"2024-01-02"` — is a real but separate defect. Fixing it here would widen this change's blast radius into the read path, where the correct fix (parsing ClickHouse's date text into a `%Date{}`) is a different concern from what a bulk write hands back.

## Risks / Trade-offs

- [The returned record carries the submitted value, not the column-truncated one] → The truncation was never visible in the wire form anyway (decision 1), so this is not a regression against the current behaviour for `DateTime64`; it *is* a change against the current behaviour for `:date`, which today comes back as an integer. The single-record `create` path has always returned the submitted value, so this makes the two paths agree.
- [A record built from the submitted attributes carries no value for a server-computed column] → Matches the single-record path and the documented "locally reconstructed" contract; the spec pins it so a future change cannot silently switch to re-reading rows.
- [`put_metadata/2` on a changeset with no bulk context] → The helper's catch-all clause returns the record unchanged; no metadata is attached and nothing raises.
- [A caller might have been relying on the current raise] → Not possible: the raise is an exception, and `return_records?: false` (Ash's default) never reaches it.
- [The record's `__metadata__` gains keys a caller did not expect] → The keys are Ash's own bulk bookkeeping, the same ones `AshPostgres` sets, and Ash reads them itself.

## Migration Plan

Ship as a patch release (version bump + `CHANGELOG.md` entry). No schema, data or API migration: what is written to ClickHouse does not change, only what the caller gets back. Rollback is reverting the change; already-stored rows need no repair.
